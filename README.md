# Skulk Client

Skulk is a Minecraft 1.21.4 Fabric client mod that analyzes a selected parkour landing, searches Minecraft movement physics for a stable route, and executes the resulting per-tick controls.

## Controls

- `G` selects and analyzes the block under the crosshair.
- `/skulk select <x> <y> <z>` selects by absolute integer block coordinates, without aiming or moving the camera. For example, `/skulk select 76 -59 42`. Use the landing block's Y coordinate, not the player's feet height.
- `H` plans and executes the current valid selection.
- `C` cancels execution and clears the selection.

A new keyboard press during planning or execution cancels the jump and releases its
movement inputs. Mouse movement does not cancel it. The initial `H` press, its key repeat,
and key releases do not cancel the jump; a fresh `H`/`G` press cancels without restarting it.

Selecting a new target cancels planning; selection is refused once movement has begun. Cancelling, disconnecting, disabling the mod, invalidating world geometry, failing execution, or timing out releases every movement input.

The coordinate command runs entirely on the client and needs no server commands or operator permission. It performs the same analysis as `G`; invalid or unloaded targets clear the previous selection. Selection does not start movement: close chat and press `H` to plan/execute, or `C` to clear. `/skulk` displays usage.

## Parkour engine checkpoint

The client pipeline is split into immutable, bounded stages:

1. `JumpAnalyzer` captures exact player state, collision-shape surfaces, distance-legal takeoff edges, the connected flat approach components behind them, and the selected block's connected same-height landing platform in a `JumpProblem`. The approach region remains available even when only its front block is within the 4.3-block level/upward jump bound, while reachable terrain below the course no longer floods the 256-surface planning input. Downward targets and potential ladder-assisted routes are not subject to that ballistic distance veto. Vertical reach has no block-count veto: partial shapes such as a block plus trapdoor reach the production simulator, which decides whether their exact collision top is attainable.
2. `ParkourPhysics` is the one immutable movement kernel used by production planning, execution prediction, recovery, landing control, and automated fixtures. Every tick returns both the next state and a collision manifold containing stable shape/face identities, contact axes, support classification, requested/resolved displacement, and pre/post-contact velocity. It preserves captured movement, jump strength, gravity, step height, effects, ground/air acceleration, sprint-jump impulse, slipperiness/drag, collision clipping, step-up, and head/side/corner contact without cloning a live player. Regular ladders use vanilla's pre-move horizontal/downward velocity clamps and post-move wall-pressure climbing impulse. State-only prediction uses identical mechanics without allocating unused contact diagnostics.
3. `SearchPlanningSession` builds fixed launch lanes and landing zones, then uses a 200 ms ordinary fast path and an adaptive collision stage. Supported ground prefixes are generated by production physics, grouped into lateral position/velocity manifolds, and ranked by the shortest sufficient staging/run-up cost. Configuration-space obstacles expand every nearby collision shape by the real player dimensions, so full columns and floating top-only pillars create the same horizontal body obstruction. Left/right homotopies follow the union silhouette of intersecting shapes rather than visiting internal block seams. Only flight branches compete in the 256-state obstacle beam; head, wall, and corner contacts remain viable in contact routes. When the conservative beam fails, a bounded tighter-clearance search preserves additional outcome diversity and rejects forbidden contacts immediately. Nominal near-misses can seed local refinements of actual approach commands; the same eight-variant contact proof remains mandatory. Search retains the 750 ms ordinary soft limit and 1.5-second collision deadline, with validation/finalization reserves.
4. `MovementPlan` records a safe staging region, the complete supported approach region, reference ground states, launch/commit window, contact contract, route topology, command-latency model, relevant configuration obstacles, guarded controls, collision/support-aware trajectory, landing zone, and structured metrics. The launch envelope is centered on the actual simulated takeoff state and includes its full forward and lateral velocity vector; contact routes reuse the eight mandatory position/speed/yaw perturbation proofs rather than inventing runtime tolerances.
5. `SupportResolver` classifies support from the player bounding box and collision-shape tops. `LandingStabilityTracker` requires eight slow grounded ticks followed by six settling ticks, so legal edge overlap can succeed while contact followed by sliding or falling cannot.

Landing anchors never move during search. Core and near-side fringe anchors are both exposed to direct search; transit clearance and collision freedom rank before landing aesthetics, while core support wins between otherwise comparable routes. Any positive, persistently stable target support is valid. Launch prefixes start from the real state, then increase available lead-up in quarter-block increments; shared ground motion does not compete for obstacle-beam capacity. The 4.3-block level/upward edge-distance limit remains a coarse horizontal bound for unassisted jumps; descending and potential ladder-assisted routes bypass it. Vertical reach is entirely simulation-governed.

Collision contact is not itself a rejection: head hits and useful side/corner contact remain valid when the expected feature, face class, timing window, and post-contact state stay inside the route contract. Before launch, the controller rotates with movement released, then uses four-tick production-physics MPC to enter a staging region without leaving the connected approach support. Close to the region, it uses six ticks and bounded yaw adjustments for finer positioning with binary keys. Two controlled observations establish staging; six observations without useful position, velocity, or yaw progress stop oscillation, and 40 ticks bound an attempt. A nearby settled state may enter only when replaying the immutable controls proves the nominal contact/landing outcome. It always rebases the reference trajectory after a passing replay. If the launch shifts outside the original envelope, contact routes require all eight sampled checks again; ordinary routes keep only the position/speed/yaw offsets that actually pass. The approach then follows that validated state tube. Automatic replanning is permitted only while the observed player bounding box remains grounded on the original approach region; losing support is terminal and releases movement instead of reanalyzing terrain below the course. Takeoff commits inside the simulation-proven launch envelope or after one supported command whose predicted result enters it. Any route may use Minecraft's exact final retained-ground tick only when the actual and predicted states agree with the launch envelope; it may never issue another approach command there. Jump is latched for at most two command epochs and acknowledged only by observed upward motion or a valid immediate head contact.

`StepExecutor` releases movement inputs while `AsyncPlanningSession` solves the route. World cells are captured on the client thread in 2 ms slices (at most 131,072 cells), then immutable `SnapshotWorld` shapes/properties are spatially indexed and searched on one cancellable background worker. No Minecraft world APIs are called from that worker. Unknown space is not treated as air. Capture/search together have an additional bounded deadline; cancellation or world changes discard the result. Execution reuses the indexed shapes and checks live block-state fingerprints, including movement properties, fluids, ladders and the neighbor halo, before commands. Expensive preparation and validation no longer run on the render thread; JVM scheduling/class-loading can still exceed individual timing targets.

For difficult avoidance routes, local shooting refinement replays the whole ground approach from nearby supported staging poses and varies the jump heading. It never invents an airborne launch state. Standard contact validation uses eight axis perturbations: position +/-0.025 blocks, forward speed +/-0.02 blocks/tick, and initial yaw +/-1.5 degrees. If no standard route passes, an explicitly labelled precision route may use +/-0.005, +/-0.003, and +/-0.35 respectively, but still requires all eight checks and stable nominal support. The runtime launch envelope and any staging revalidation use these same narrower bounds; it cannot accept the old wider errors. This is sampled validation, not a mathematical guarantee for every combination of perturbations. Requested takeoff yaw must be reachable within the actual 12-degree command rotation limit. Ordinary routes retain their existing fast path and tolerances.

Execution crosses an injectable `MovementIO` boundary: command epoch N advances only after the next observation reports that epoch, so controls cannot be consumed twice or landing commands applied in flight. Runtime phases are `STAGING`, `APPROACH_TRACKING`, `TAKEOFF_COMMITTED`, `CONTACT_TRANSIT`, and `LANDING`. In flight, monotonic ±2-sample matching preserves the validated control inside a conservative deadband; genuine divergence invokes a four-tick MPC over planned, neutral, brake, left, and right actions. Recovery scores the resulting trajectory and forbids unplanned configuration-obstacle contact. The observed current state is compared with the current predicted sample, while candidate commands are compared with the next sample, preventing the former one-frame correction offset. Staging deduplication uses numeric state keys; short-horizon yaw refinement holds or resets a chosen heading instead of branching redundant camera changes at every depth.

Ladder support includes standing on a regular ladder's thin top, jumping from it, landing on it, and successive ascending corner transfers around a tower, in addition to five-block, offset, adjacent-face and hidden/back-face catches. Select the rung itself when its top is the desired endpoint; select the full platform when climbing onto that platform is the goal. `SupportGeometry` finds body-clear feet regions with positive footprint support, so a rung is not discarded for being thin or for having its center inside the backing wall. Launch diversity preserves both ends of narrow supports instead of filling every slot with nearby duplicate headings. `LadderColumn` separately models feet-cell attachment: touching the thin collision shape is not sufficient to climb. `LadderContinuation` shares bounded climb/hold/exit control between search, validation and execution; attached recovery has its own bounded climb window. Hanging starts, vines, scaffolding, trapdoor-assisted climbing and liquids remain outside the validated domain. See the [top-support/timing checkpoint](docs/TOP_SUPPORT_AND_TAKEOFF_CHECKPOINT.md) for exact geometry, results and remaining limitations; the [previous niche checkpoint](docs/NICHE_AND_LADDER_CHECKPOINT.md) remains historical evidence.

Input history is part of the physics state. Minecraft's float arithmetic, sine lookup, sprint modifier, previous sneak pose, soft/hard collision sprint cancellation, and seven-tick forward double-tap timer are preserved. The one client-only access-widener entry exposes that timer for read-only capture; it does not reset the timer or alter vanilla sprint behavior. Staging always replays the full route from the observed state, including residual velocity and input history, and rebases the reference prefix even if the resulting launch already fits the old envelope. Contact routes require the full sampled tube when rebased; ordinary routes retain only offsets that actually pass, including one-sided or zero-width ranges. Before leaving support, the executor checks the departure and following jump together rather than discovering a missed launch after walking off.

Sprint eligibility is captured from actual hunger and flight permission. Low hunger cannot
produce sprint acceleration or a sprint-jump boost merely because a simulated frame requests
the sprint key. Exhaustion over an entire future route is not forecast; execution resamples
the real state before issuing commands.

Sneak has a hard safety boundary. It is illegal in positioning, run-up, takeoff, and ordinary airborne frames. Execution only permits it on actual target ground support or in the explicit `LADDER` phase while the real feet block is a regular ladder. Losing ladder attachment immediately clears that permission; Shift does not enlarge the grab volume. The kernel preserves previous-input crouch slowing, the captured sneaking-speed attribute, and end-of-tick pose changes. After landing, 14-tick natural-friction and closed-loop counter-input rollouts are preferred; sneak is reevaluated each tick and used only when all tested non-sneak options would leave support. Sneak edge clamping limits displacement without falsely zeroing residual velocity.

Overhead obstacle discovery covers the ballistic body-height range, not only the straight line between feet positions. Supported perimeter launch lanes and bounded control-knot shooting can move around low overhangs and hidden ladder faces; shared ground prefixes remain physically generated. A discovered narrow catch is refined and validated immediately instead of spending the remaining deadline enumerating unrelated candidates. Ladder validation uses the same closed-loop attachment controller as execution and requires eight passing standard or explicitly narrower precision launch checks. The exact final retained-ground launch exception is independent of later contact type, but still requires the predicted final state and matching launch envelope and can only issue jump, never another run-up tick.

Rendering distinguishes the connected landing region and sampled core (red), fixed settle anchor, launch corridor/takeoff footprint and commit window (blue), staging region and positioning path (gray), required momentum (cyan), predicted flight/landing trajectory (green), configuration-space obstacles (purple), and required contact faces (magenta).

The obsolete live-player simulator, all-in-one beam boundary, and fake fixture physics were removed. The extracted physics kernel retains the LiquidBounce-derived notice. Server and license behavior are outside this checkpoint.

## Verification

Run the automated checkpoint from the repository root:

```powershell
.\gradlew.bat clean build --warning-mode all
.\tools\audit-client.ps1 -JdkPath $env:JAVA_HOME
```

The read-only audit follows compiled class references from Fabric entrypoints, registered
mixins, and retained license classes. It fails on unreachable source units, missing internal
references, test artifacts leaking into the shipping jar, or new unaudited access-widener entries.

The JUnit suite runs the production kernel against an in-memory collision-shape world and covers exact movement sequences; underside, side, corner, swept, and support manifolds; floating/full-pillar topology; ordinary and maximum-reach jumps; shifted targets; partial-shape rises; stable fringe landings; required head contact; geometry-derived avoidance; eight-variant contact tubes; delayed command/observation execution; wrong-facing stationary alignment; staging stall cleanup; unsafe-replan refusal after support loss; nominal headhitter/avoidance replay; airborne correction indexing; pre-landing sneak prevention; world invalidation; timeout/cancellation; duplicate-start refusal; and terminal input cleanup.

### Real Minecraft trials

Use JDK 21. The separate `gametest` source set is a development-only mod; its entrypoints,
mixins, fixture commands, telemetry, and watchdog are **not packaged in the shipping jar**.
No personal saves, multiplayer worlds, server code, or license code are modified.

```powershell
# Creates and runs an isolated, disposable integrated world.
.\gradlew.bat runClientGameTest "-PtrialCases=coordinate-selection,movement,fractional-strafe,gap-1,gap-2,gap-3,gap-4,headhitter,neo,floating-neo"

# Uses normal client/server tick scheduling, without Fabric GameTest timing overrides.
# The first launch may show Minecraft's accessibility welcome screen: choose Continue.
.\gradlew.bat runParkourLive "-PtrialCases=gap-4,headhitter,neo,floating-neo" "-PtrialRepeats=3"
```

The second command copies a world generated by the first into
`build/run/parkourLive/saves/Skulk Trials`. A marker and exact save-path check restrict
fixture mutations to this disposable world. A pre-existing unmarked destination is refused.
`clean` removes these generated worlds and results; archive evidence before cleaning.

`trialCases=all` runs every fixture. Additional cases are `wrong-yaw`, `headhitter-back`,
`neo-left-start`, `neo-right-start`, and `neo-back`. Capability fixtures also include `double-neo`,
`floating-double-neo`, `double-neo-right-start`, `double-neo-back`, `ladder-calibration`, `ladder-catch`, `ladder-catch-north`, and
`ladder-catch-wrong-yaw`. The expanded catalog adds `ladder-hold-calibration`, `overhang-rise`,
`overhang-rise-north`, `overhang-rise-wrong-yaw`, `offset-gap-4`, `trapdoor-rise`, `slab-drop`,
`fence-landing`, `stair-rise`, `late-ceiling`, `ladder-catch-gap-5`, `ladder-catch-offset`,
`ladder-catch-side`, `ladder-catch-back`, `ladder-catch-side-north`, `ladder-catch-back-north`,
and `ladder-catch-gap-5-single-rung`. The top-support pass adds `oblique-calibration`,
`sprint-tap-calibration`, `tight-offset-0` through `tight-offset-3`, `tight-offset-moving`,
`tight-one-runway-0` through `tight-one-runway-2`, `tight-two-runway`, `ladder-top-land`,
`ladder-top-start`, `ladder-top-north-start`, `ladder-top-rise`, `ladder-top-corner`,
`ladder-top-back`, `ladder-tower-clockwise`, and `ladder-tower-counterclockwise`.
The opposite-face single-rung `ladder-top-back` is an exploratory capability probe, not a
promised successful route. Tower fixtures select four successive higher rungs with no
teleport, velocity reset, or camera reset between legs.
Unknown names fail instead of silently
skipping coverage; repeats must be between 1 and 20.

Each jump uses the real `/skulk select` chat-command path and H keybinding. Fixture setup
may teleport/reset the player, but once a trial begins the harness does not move the
player, change velocity, override collisions, or replace vanilla movement. Skulk controls
the keys/yaw through its normal executor. Completion independently requires real grounded
collision-shape support for 40 ticks **after inputs are released**, plus no unguarded airborne sneak
(actual ladder holding is recorded separately from an ordinary-flight violation).
Headhitter fixtures must actually record a ceiling contact; ladder-catch fixtures must actually
enter the climbing state. Jump trials check both raw-key and issued-command prediction error
below 0.002 blocks/tick. Diagnostic prediction must not use the post-input sprint state as
the sprint key: doing so concealed automatic double-tap sprint in earlier trace summaries.

Before each trial, setup restores and verifies full food/saturation, clears the temporary
effect, and verifies every command-placed ladder after neighbor updates: correct facing,
surviving block, and vanilla backing-support check. Each `.preflight.json` records the
results. No feeding or geometry repair occurs during execution. Food level is recorded
throughout; a capability trial that loses sprint permission is labelled invalid, not used
as evidence that the solver cannot perform the jump.

Timestamped `build/parkour-results/*-{gametest,realtime}` directories contain `summary.json`,
per-tick `.jsonl` actual/command/prediction traces, plan/search/candidate dumps, and
`.timings.json` client planning/execution/idle timings (count, median, p95, maximum). These measure
Skulk's tick work, not total GPU frame time. Screenshots
are in the respective run directory's `screenshots` folder. Consumed-input physics error and
issued-command error are distinct: the latter also exposes input/yaw/sprint mismatches.
`-PtrialBeams=true` additionally captures full beam dumps. Leave it off for timing runs:
reflecting and retaining every search state adds allocation and profiling overhead.
The normal runner fails on command/observation stalls, writes a JVM thread dump, requests
cleanup, and terminates only its own disposable JVM if shutdown remains blocked for five
seconds. Startup is bounded to two minutes. `-PtrialFreeze=true` intentionally stalls that
test client's render thread to exercise the watchdog; this negative test must fail.
The watchdog is an independent Java thread, not an external process supervisor: a total JVM
or operating-system stall remains outside its coverage. Fabric Loader may warn about absent
Kotlin output directories because these source sets contain no Kotlin; this is an external
development-classpath warning, not a source compilation warning.

These generated courses are regression fixtures, not the user's original parkour map.
Passing them is evidence for those exact starts and geometries, not a claim that every
neo or arbitrary collision route works. Real traces found ceiling-velocity and corner-axis
physics mismatches, fractional inputs that binary keys could not execute, and launch-state
starvation. Contact-route launches now prove their required position support offsets before
entering the flight beam, so unsupported perturbations cannot monopolize its validation budget.
